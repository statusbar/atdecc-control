# Folded schema data — provenance

The GALAXY 816 namespace starts from the programming guide's template
table (`galaxy_schema.cpp`, the guide layer) and is then overlaid with
data folded from a live device. Every folded layer is regenerated by
`python/galaxy/fold_describes.py` into
`statusbar/controlplane_devices/galaxy_schema_ranges.inc` and gated by
ctest (`galaxy_ranges_check` runs the fold in `--check` mode and fails
on any drift between the committed table and the captures).

## Ground truth

All captures are from one device: a production GALAXY 816 ("Q1",
firmware 2.10.0-20260211-1241), recorded with its owner's permission
over the proxy host (see OPERATIONS.md). The unit is **in active use**
— its current processing state is live venue state, not factory state.

| file | contents |
| --- | --- |
| `captures/q1-live-dump.tsv` | all 9766 paths with live values (2026-08-29) |
| `captures/q1-describe-*.txt` | `?path` describe responses for all 9766 paths |

The captures are byte-faithful to the device except for seven values
blanked before publication because they identify the venue rather than
the device: the connected talker on AVB input 9 (entity ID, name, group),
the management network address, mask and gateway, and the log line. The
reconciliation that produced them reported 9766/9766 schema points,
0 unknown, 0 missing.

## The folded layers

1. **Ranges and units** (220 shapes): the describe `minimum`/`maximum`/
   `step`/`units`, keyed by path shape (numeric segments → `#`, except
   U-Shaping band numbers, whose ranges are per-band). GALAXY unit
   strings map to AEM unit codes (`UNIT_CODES` in the fold script).
   Delays are in **samples** (0–48000), not seconds.
2. **Enum label lists** (26 per-shape tables, 293 labels): verbatim
   `value:NAME` strings, uniform per shape, served back in the `?`
   describe response.
3. **Aliases** (all 9766): the device's `@N` item indices, dense
   0..9765, not derivable from any path ordering. Folded as
   `GALAXY_ALIASES` in alias order; `GalaxyNamespace` binds both
   directions and `resolve_address`/`resolve_selection` accept `@N`
   anywhere ASCII meets the namespace. The device always *replies*
   with canonical paths, never aliases.
4. **Human-readable names** (all 9766): the device's identical
   `name`/`description` strings, verbatim — including 4985 leading
   spaces (firmware formats `"<prefix> <label>"` with an empty prefix)
   and one apostrophe. These replaced the path-derived `humanize()`
   guess, which disagreed with the device on 7870 points.
5. **Defaults** (from `q1-live-dump.tsv`): the dump corroborated the
   guide on 8860 points. For the 906 disagreements, the curated
   `LIVE_DRIFT` table in the fold script decides:
   - listed shapes are operator/venue state on the in-use unit (input
     mutes/gains, matrix routing, input modes, snapshot data, access
     table), and `/entity/*` (the unit's identity) and `/status/*` (a
     telemetry snapshot of its moment) are never defaults — the guide
     default in the template stands for all of these (`def` emitted as
     `nullptr`; the template's serial number is empty);
   - everything else is firmware 2.10 factory/representative state,
     verified uniform across strips/outputs/bands where applicable
     (U-Shaping frequencies doubled vs the guide, slopes 2 → 1,
     per-band delay-integration/allpass ladders, beam angles).

   NOT folded: the describe `default` field itself — the device
   reports its generic control-DB init there (e.g. every EQ band
   frequency "1000"), contradicting both the guide and observed state.

## Per-model meter banks

`GalaxyModelBanks` (`galaxy_aem_model.{hpp,cpp}`) sizes the AEM meter
banks per `/status/model_string`. The family shares one DSP engine —
"The GALAXY 816 processor has the same audio processing capability in
a 2RU chassis with different physical I/O" (GALAXY 408 datasheet) — so
matrix-input meters (32) and output meters (16) are family-wide;
physical banks follow the connectors:

| model | inputs | SIM buses | line_mon | status |
| --- | --- | --- | --- | --- |
| GX-408 | 4 | 1 | 8 | datasheet-derived, provisional |
| GX-816 | 8 | 2 | 16 | **live-verified** (the Q1) |
| GX-816-AES3 | 8 | 2 | 8 | datasheet-derived, provisional |

Unknown model strings (including the guide-listed Bluehorn 816, whose
control surface is undocumented) fall back to GX-816. The reference
network's GALAXY 408 is AVB-only from the proxy's segment — no ASCII
reach — so the 408 row awaits a reachable device for live
verification.

## Cross-checks and gates

| gate (ctest) | what it verifies |
| --- | --- |
| `galaxy_ranges_check` | the committed `.inc` matches the captures exactly |
| `galaxy_namespace_check` | every guide shape generated; every generated shape in guide or on device (curated PDF-artifact fixups and verified device typos in `check_namespace.py`) |
| `galaxy_describe_roundtrip` | the `?` describe response parses as a Python literal AND a JavaScript expression (every value quoted; enum lists as string lists) |

## Regeneration

```sh
uv run python python/galaxy/fold_describes.py   # rewrites the .inc
```

Refreshing the captures requires the live device (read-only `?path`
and value gets over the tunnel). The fold errors out rather than
guessing: unmapped unit strings, non-uniform enums/ranges per shape,
non-dense aliases, `name != description`, or a dump/describe path-set
mismatch all abort the fold.
